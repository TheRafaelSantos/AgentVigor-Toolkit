# Managed Graphify configuration / Configuração gerenciada / Configuración gestionada

## English

`lib/graphify-integration.mjs` exports `configureGraphify` and `graphifySource`.
This optional integration configures an **existing** official `graphifyy==0.9.102`
executable. It does not install or upgrade the executable. A missing executable
fails with `GRAPHIFY_MISSING`; another version fails with `GRAPHIFY_UNRECOGNIZED`.
The audited upstream commit is
[`59b5ab1`](https://github.com/Graphify-Labs/graphify/tree/59b5ab1151e031fb42e39cfc9a50bf96f2d57ae0).

The library API accepts `{ home, env, agent: 'codex' | 'claude',
mode: 'configure' | 'rollback', executable, dryRun, expectedPlan }`.
Use an absolute executable path. `dryRun: true` returns changed paths and
`planToken`, without exposing private instruction content. Review the plan before passing
that same token as `expectedPlan` for application. No token means no destination
writes. Changed files, state or executable bytes invalidate the reviewed plan.

The preview uses bundled, hash-checked official assets and runs **only
`--version`**, with an isolated temporary home and an environment that excludes
provider keys and Python import overrides. It does not execute the initializer,
download packages, contact a model or configure credentials. Confirmed application
runs `graphify install --platform codex|claude` inside a separate temporary home,
validates all generated bytes against the reviewed files and then uses the shared
durable transaction to write the destination. This subprocess is isolation by
configuration, not an operating-system security sandbox. The selected executable
and its Python installation must be trusted. Executable hash binding alone does
not authenticate the complete Python environment; generated assets are also
checked against the audited bundle before destination writes.

Owned files are `skills/graphify/SKILL.md`, eight reference sidecars,
`.graphify_version`, Apache-2.0 `LICENSE`, preserved `LICENSE-MIT`, and `NOTICE`.
For Claude, `CLAUDE.md` receives the upstream registration with the final skill
path; preexisting user instructions and their CRLF/LF convention are preserved.
An unmanaged `# graphify` registration is refused instead of replaced. Unmanaged
Graphify directories and conflicting native/legacy copies are also refused.

Codex's upstream installer uses `~/.codex/skills/graphify` and ignores
`CODEX_HOME`. The temporary generator follows that upstream destination, while
AgentVigor explicitly maps the checked bytes to
`${CODEX_HOME:-~/.codex}/skills/graphify`. Before doing so it checks
`~/.codex/skills/graphify` and `~/.agents/skills/graphify` for competing copies.
Claude honors `${CLAUDE_CONFIG_DIR:-~/.claude}`; a custom root also checks the
default Claude root. No existing copy is adopted, moved or deleted automatically.

Rollback previews and restores the saved preinstallation bytes without requiring
the executable. The shared state is under
`~/.agentvigor/integrations/graphify-<agent>/state.json`. Locks, interrupted-write
recovery and drift checks apply. Edits to managed files block rollback rather
than being overwritten; unrelated extra files are preserved. There are no project
hooks, project instruction changes, MCP setup, provider/model changes or API
spending. `discovered` and `verified` remain `UNVERIFIED` until observed in a
fresh native-client session and a scoped invocation.

Run from the repository root, in PowerShell or a Linux shell:

```text
node --test test/graphify-integration.test.mjs
node scripts/smoke-graphify.mjs /absolute/path/to/graphify
```

On Windows, pass the full quoted `.exe` path instead of the Linux example.
The smoke test writes only disposable roots, verifies Codex and Claude custom
root mapping, idempotency, and rollback, and then removes those roots. It never
installs a prerequisite and reports a missing path explicitly. A passing smoke
test proves configuration transactions, not discovery or model-backed execution.

## Private executable and client configuration

Run these commands from the checkout in PowerShell or a Linux shell. The first
operation requires `uv`, an existing Python 3.10 or newer, and access to PyPI.
The private runtime uses the pinned base package. `verify` checks local package
integrity and the reported version. The selected client is configured separately.

```powershell
node bin/agentvigor.mjs integrations --tool graphify --scope binary --mode install --dry-run --json
node bin/agentvigor.mjs integrations --tool graphify --scope binary --mode install
node bin/agentvigor.mjs integrations --tool graphify --scope binary --mode verify --json
node bin/agentvigor.mjs integrations --tool graphify --agent codex --mode configure --dry-run
node bin/agentvigor.mjs integrations --tool graphify --agent codex --mode configure
```

Use `--agent claude` for that client. The CLI uses the verified private executable
when present. For a session to run Graphify by name, expose the private runtime's
`bin` directory in that session's PATH or use its absolute executable path.
Remove any managed client configuration before rolling back its private runtime.

```powershell
node bin/agentvigor.mjs integrations --tool graphify --agent codex --mode rollback
node bin/agentvigor.mjs integrations --tool graphify --scope binary --mode rollback
```

## Português brasileiro

A integração opcional configura um executável oficial **já instalado**, exatamente
`graphifyy==0.9.102`. Não instala nem atualiza o programa. `GRAPHIFY_MISSING`
significa executável ausente; `GRAPHIFY_UNRECOGNIZED` indica versão ou saída
incompatível. A API exportada é `configureGraphify`, com os parâmetros descritos
acima, e `graphifySource` identifica versão, origem, commit e licenças.

1. Gere a prévia com `dryRun: true` e caminho absoluto em `executable`.
2. Revise `files`, `changes` e `planToken`. A prévia é offline: utiliza arquivos
   oficiais empacotados e executa somente `--version` com HOME temporário.
3. Aplique com `expectedPlan` igual ao token revisado. Somente nessa etapa o
   instalador oficial global roda em uma pasta temporária; todos os arquivos
   gerados precisam coincidir com a prévia antes da escrita final.
4. Para reverter, use `mode: 'rollback'`, gere outra prévia e aplique seu token.
   A reversão não depende do executável. Os bytes anteriores ficam no estado
   durável em `~/.agentvigor/integrations/graphify-<agent>/state.json`.

São gerenciados a skill completa, oito referências, marca `0.9.102`, licenças
Apache/MIT e NOTICE. Claude recebe o registro no `CLAUDE.md`, com normalização
do caminho temporário para o destino definitivo. Instruções do usuário são
preservadas. Cópias não gerenciadas, registros `# graphify` preexistentes e
duplicatas nos diretórios nativos/legados bloqueiam a operação. Arquivos
gerenciados editados depois da instalação bloqueiam a reversão; não são apagados.

Para Codex, `CODEX_HOME` é uma adaptação explícita do AgentVigor: o gerador original
ignora essa variável e usa `~/.codex`. Para Claude, `CLAUDE_CONFIG_DIR` já é
suportado pelo original. Os testes oficiais usam destinos personalizados para
validar esse mapeamento. Nenhum hook ou arquivo de projeto é alterado; não há
mudança de modelo, provedor, credenciais nem chamadas de API. Descoberta e
invocação continuam `UNVERIFIED` até observação real no cliente nativo.

No PowerShell, dentro da pasta do projeto, execute o comando de testes acima.
O resultado esperado é zero falhas. Para validar com o programa oficial,
execute `node scripts/smoke-graphify.mjs` seguido do caminho completo entre
aspas para o `graphify.exe` 0.9.102. O resultado esperado são duas mensagens de
sucesso, uma por cliente. Não execute um upgrade global para cumprir esse teste.

O isolamento usa variáveis e pastas temporárias, não uma sandbox de segurança.
Confie no executável e no ambiente Python selecionados. O hash vincula o binário
à prévia, mas não autentica todas as dependências Python; os arquivos gerados
também são comparados com a origem auditada. Não foram comprovadas economia de
tokens, descoberta automática ou execução com modelo.

## Español

La integración opcional configura un ejecutable oficial **ya instalado** de
`graphifyy==0.9.102`; no lo instala ni actualiza. `GRAPHIFY_MISSING` indica que
falta el ejecutable y `GRAPHIFY_UNRECOGNIZED` rechaza otra versión o salida.
`configureGraphify` y `graphifySource` son las exportaciones de la biblioteca.

Primero use `dryRun: true` y revise `files`, `changes` y `planToken`. La vista
previa es offline: utiliza el paquete auditado y ejecuta solamente `--version`
con HOME temporal. Aplique pasando el token como `expectedPlan`. Solo entonces
se ejecuta el instalador oficial global en otro directorio temporal y se comparan
todos los bytes generados antes de escribir el destino mediante una transacción
duradera. Cambios en archivos, estado o ejecutable invalidan la aprobación.

Se incluyen la skill completa, ocho referencias, `.graphify_version` y las
licencias Apache/MIT/NOTICE. Claude también recibe el registro de `CLAUDE.md`
con la ruta definitiva y conserva instrucciones previas. Las instalaciones no
gestionadas, duplicados y registros `# graphify` previos se rechazan. Codex usa
una adaptación explícita de `CODEX_HOME`, que el instalador original ignora;
Claude respeta `CLAUDE_CONFIG_DIR`. Se comprueban destinos nativos y heredados.

Para revertir, genere y aplique otra vista previa con `mode: 'rollback'`.
No se necesita el ejecutable. Se restauran los bytes guardados en
`~/.agentvigor/integrations/graphify-<agent>/state.json`; cambios posteriores en
archivos gestionados bloquean la reversión y los archivos ajenos se conservan.

Ejecute los comandos de prueba anteriores desde la raíz del repositorio, usando
una ruta absoluta al ejecutable oficial. En Windows, use la ruta `.exe` entre
comillas. El smoke test prueba configuración, repetición y reversión en raíces
desechables para ambos clientes. No instala requisitos ni altera hooks de
proyecto, modelos, proveedores o credenciales. No llama APIs. Descubrimiento e
invocación permanecen `UNVERIFIED` hasta observarlos en el cliente nativo.

El aislamiento por entorno no es una sandbox de seguridad: el ejecutable y su
entorno Python deben ser confiables. El hash del binario no autentica todas las
dependencias; también se validan los archivos generados contra el paquete
auditado. No se afirma ahorro de tokens ni descubrimiento automático.
